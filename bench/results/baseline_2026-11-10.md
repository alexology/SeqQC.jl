## Command and inputs

```
SEQQC_BENCH_REPS=2 julia --project=. --threads=1 bench/run_benchmarks.jl <scratch>/bench \
    <real_ont_reads>.fastq.gz
```

- Synthetic inputs as described in `docs/BENCHMARKS.md` (generated in a scratch directory, not stored).
- Real input: `real_ont_amplicons.fastq.gz`, untrimmed ONT amplicon reads (ND2–COI, ~2.8 kb), unpublished
  data, read in place from a local disk; not stored in the repository (file name anonymised).
- Code state: Phase 1 as of 2026-11-10, before `read_quality_of_mean_error` was added (one extra
  floating-point addition per read; not re-measured).
- Julia start-up plus `using SeqQC` (precompiled): 0.57 s (`time julia --project=. -e "using SeqQC"`, one run).

## Observations

- gzip inputs: decompression dominates. On the real file FASTX parsing (with decompression) takes
  10.8 s of the 14.4 s SeqQC run; SeqQC metrics add about 3.6 s (25%).
  The "decompress" stage copies 1 MiB blocks with `readbytes!` and is slower than FASTX reading the
  stream buffer directly, so it is not a strict lower bound.
- Plain inputs: the per-read summary pass costs more than parsing (Illumina-like: parse 0.24 s,
  ReadLength-only 0.54 s, default 0.72 s). The likely cause is the serial floating-point sum of
  error probabilities (one dependent addition per base), computed even when no metric needs quality;
  to be verified by profiling in Phase 2.
- Allocations: about 16 B per read come from FASTX itself (the same with `iterate` and with
  `read!` into a reused record, measured separately on 100,000 reads); the SeqQC engine adds no
  measurable per-read allocation. The remaining bytes per read in the table are the fixed
  per-call allocations (metric states, result) divided by the reads.
- No comparison of speed with other tools was made.
